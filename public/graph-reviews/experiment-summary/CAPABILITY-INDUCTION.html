Blind hierarchical capability induction

The flat grouping experiment answered a narrower question than the product asks. It compared ways to partition commits into same-level groups. A repository capability can instead be an umbrella containing narrower behaviors, and one commit can support several capabilities. A flat partition cannot represent either fact.

npm run induce-capabilities tests a different formulation: show one model the complete set of saved per-commit readings and ask it to infer a hierarchy directly. It receives no maintainer taxonomy, no desired capability count, and none of the earlier clusters.

The September 6 iterative graph experiment builds on the saved leaf discoveries to test arbitrary depth, dependencies, source retrieval, and downward revision. The two-level results below remain the original experimental condition.

Experimental contract

The induction prompt makes five choices explicit:

  1. A capability is a durable outcome or behavior recognizable to a user, developer, or operator, rather than a directory, framework, layer, phase, or implementation step.
  2. Several narrower behaviors may sit beneath one umbrella capability. The current experiment emits at most two levels: umbrella plus optional children.
  3. A cross-cutting commit may support more than one capability.
  4. A capability may cover any fraction of the repository. Size alone cannot reject it.
  5. Routine or ambiguous work may remain unassigned.

The model attaches numbered readings to the most specific nodes it directly supports. The parser resolves those numbers back to commit SHAs, derives each ancestor's rolled-up evidence, reports unassigned and overlapping commits, and rejects unsupported nodes. Raw provider output is written before parsing and can be replayed with --response, so a validation change never requires buying the inference again.

Two levels are a deliberate present boundary, not an ontology. A larger or longer-lived repository may support broader umbrellas above today's capabilities, or further useful structure below them. The output is recursively shaped so later experiments can permit that without a schema migration; the prompt and validator simply stop at two today.

This hierarchy is also orthogonal to epochs and eras. Epochs organize when the work changed character. Capability umbrellas organize what the system does, and one capability may cross several epochs. A future view may relate the two axes, but neither should be forced to stand in for the other.

Held-out owner audit

Only after the run completed was the generated hierarchy compared with the owner's rough list. It independently named counterparts for the list's major concepts: course search and filters, professor pages, grade distributions, comparison, review submission, landing/site experience, editorial blog, ETL, and deployment/monitoring.

That is a promising recall check, not a score. The list did not define exact membership or parent-child relationships, and matching names do not prove that the cited commits are right. In particular, the model used overlap for only six commits despite being allowed to use it, and this is one run from the same model family previously used for consolidation.

The owner list remains held out. It must not be inserted into the induction prompt or used as a target taxonomy for tuning this repository. Its role is to expose conspicuous misses after autonomous discovery, as it already exposed the flat methods' granularity error.

Repeated-run stability

The first pilot is not part of the formal repeatability measurement because the explicit two-level sentence was added to the prompt after that request. Three fresh runs used the same 605 readings, model, complete prompt, parser, and two-level boundary. Every parsed document carries a SHA-256 fingerprint of the complete request; the comparator refuses to claim identical protocols when the fingerprints are absent or different.

npm run compare-capability-inductions matches nodes only by cited commit sets. Names are retained in the report for inspection but never enter matching or any score. It reports:

  • maximum-weight one-to-one Jaccard matches between umbrella evidence sets and between child evidence sets;
  • commit-pair co-membership, which exposes splits and merges even when node counts differ;
  • whether independently matched children recur beneath independently matched parents;
  • assigned, unassigned, and multiply assigned commit-set agreement.

They establish a pre-critic baseline and identify where more evidence or a separate decision pass is needed: child boundaries, cross-cutting assignment, and a small set of split/merge alternatives. The full reports and raw provider responses remain ignored under public/ because they contain repository and provider metadata.

Fixed-hierarchy evidence assignment

npm run assign-capability-evidence separates two semantic decisions that induction made at once. It receives one discovered hierarchy—IDs, names, summaries, audience, and parent- child structure—but none of that run's prior commit memberships. It then reconsiders all 605 readings globally and assigns each to zero, one, or several of the fixed nodes.

The three clean discovery maps were each assigned once under one shared assignment protocol. The full requests intentionally differ because their candidate maps differ, while a second fingerprint proves that the model, instructions, readings, and output contract are the same. The parser rejects unknown capability IDs, makes omissions explicitly unassigned, retains fixed nodes even when they receive no evidence, and removes ancestor assignments that merely duplicate a more specific child.

But another model pass is not sufficient by itself: the principal remaining instability is which child capabilities exist and where their boundaries lie. Because the three assigned maps above still changed the hierarchy and the assignment sample together, a second experiment held the first clean hierarchy constant.

Disagreement critic experiment

npm run build-capability-disagreements turns repeated assignments into a deterministic review dataset. For the fixed-map runs it found the same 116 unstable commits and selected 87 reference exemplars only from commits whose complete direct assignment was identical in all three runs. The saved dataset retains the exact alternatives and their frequencies for measurement after the fact.

npm run critic-capability-disagreements gives an evidence-reading critic the fixed hierarchy, those provisional exemplars, and all 116 disputed readings. It receives no owner taxonomy, run identity, vote count, or exact assignment alternative. The first arm did show the unordered union of capability IDs previously proposed for each commit. A blinded control withheld that union as well. Both responses covered every input and cited only valid capabilities and exemplars.

Each arm was run three times with an unchanged request fingerprint. The four added responses cost $0.6617; all six responses cost $1.0247.

The complete cross-arm agreement never reaches the least-agreeing blind-with-blind pair, and the same separation appears in selected-edge F1. Showing candidate IDs therefore has a repeatable anchoring effect on this model, repository, map, and disagreement set; the one-sample difference was not just critic randomness. The visible arm kept substantially more prior edges and selected the full prior union almost twice as often.

Both Dependabot commits were marked map_insufficient in all three blind runs. They were also marked that way in one of three visible runs, while the other visible runs assigned them to an existing node. This is a stronger, still provisional signal that durable dependency automation may be absent from the hierarchy and is a concrete input for the hierarchy critic.

The architecture should default to a blind critic. Earlier alternatives belong in the post-decision comparison, not in the critic's evidence. Neither critic output is a truth set, and neither has been installed as the repository's canonical assignments. The result also does not establish that the blind answers are more correct; it establishes that the visible answers are conditioned by IDs they were shown.

Hierarchy critic pilot

npm run build-capability-hierarchy-review now creates a deterministic review packet from the current 37-node hierarchy, the other two blind hierarchy runs, the fixed-map disagreement dataset, and all three blind assignment critics. Matching between hierarchy runs uses cited evidence sets rather than labels. The packet contains two recurring map-gap signals, 74 same-depth boundary comparisons, seven unmatched alternative nodes, stable current-node exemplars, and 178 sampled commit readings. It does not contain a maintainer taxonomy.

npm run critic-capability-hierarchy reviewed that packet without mutating the hierarchy. The request used 55,814 input tokens and cost $0.1710. Its response reviewed all 37 current nodes, accounted for all 83 structural signals, used only valid node, signal, and reading IDs, and produced two supported candidate changes:

  1. Add Dependency update automation beneath Deployment and operations, citing the two Dependabot readings, both recurring blind map-gap signals, and the matching unmatched node from another blind hierarchy. Confidence: high.
  2. Split Growth loops and product analytics by promoting its two existing children— Sharing, referrals, and email capture and Product analytics and experiments—to top-level capabilities. Both other blind hierarchies independently placed analytics at the top level. Confidence: medium.

The other 78 signals remained unresolved rather than being converted into changes. Neither proposal has been applied. This establishes that the LLM can make sparse, evidence-cited structural proposals from model-generated disagreements without an owner answer key. It does not establish that either proposal is correct or repeatable. The same model family produced and reviewed the maps, alternative candidate labels remain visible in this first packet, and static inclusion of 178 readings already consumed a 55.8k-token prompt. Before revising the hierarchy, repeat the critic and measure proposal recurrence. Before scaling to larger repositories, replace the static evidence bundle with bounded on-demand retrieval.

Focused packet and repeatability

The first attempt to repeat the complete request was rejected before inference because its 30,000-token completion ceiling exceeded the remaining provider credit; it incurred no additional model cost. Rather than change that request and call it a repeat, the builder now supports a separately fingerprinted focused condition. It keeps every recurring gap and unmatched alternative, retains one stable exemplar per current node, and selects the 24 lowest-overlap boundary comparisons without looking at the first critic's proposals. This reduced the packet from 178 to 86 readings and from 203,781 to 90,697 prompt characters.

One focused Grok 4.6 run was complete: it accounted for all 33 retained signals and cost $0.0871. It retained the dependency-automation addition, but replaced the full packet's growth/analytics split with two proposed merges. Because both the packet and output ceiling changed, this is a context-selection ablation rather than a repeatability sample. It shows that retrieval is part of the semantic method, not merely a way to reduce token cost.

Three identical focused runs with Gemini 2.5 Flash Lite cost $0.0097 total. Their label-independent proposal-target agreement was poor:

measurement minimum mean maximum
operation-and-target F1 13.3% 24.9% 47.1%
operation-and-target Jaccard 7.1% 15.2% 30.8%

Only one change recurred in all three runs: add dependency automation beneath operations. All three gave it high confidence and cited exactly the same two readings and recurring gap signals. Three merge targets recurred in two runs, with 62.5–71.4% cited-evidence Jaccard. Those broader results are not eligible to revise the map: the cheap model accounted for only 2–3 of 33 signals in each run, sometimes emitted unsupported fields or no-op reparenting, and therefore failed the complete-review quality gate every time. The parser now rejects no-op reparenting, while the comparison report preserves incomplete runs for measurement and marks them ineligible for automatic revision.

The dependency gap is now unusually recurrent across assignment critics, alternative blind induction, both Grok packet conditions, and all three cheap-model repeats. It remains a candidate rather than an applied node because the only repeated hierarchy-critic condition failed its overall coverage contract. The next architecture should make evidence retrieval iterative and fail closed on incomplete review, then repeat a capable-model condition before materializing any change.

Staged retrieval pilot

The first staged critic separates semantic choice from budget enforcement:

  1. A planner sees the complete provisional hierarchy, all 33 focused structural signals, and a date-and-subject evidence catalog, but no reading interpretations.
  2. A deterministic broker validates every requested ID, schedules requests across signals, and caps the retrieved union.
  3. The hierarchy critic sees only the broker-selected readings. Planner explanations and rejected requests are deliberately omitted so the cheap planner cannot linguistically anchor the structural judgment.
  4. The existing parser validates proposal citations and requires every current node and signal to be accounted for. The hierarchy remains unchanged.

The Gemini 2.5 Flash Lite planner covered all 33 signals with valid IDs but requested 69 of the 86 available readings despite a 32-reading limit. The initial fail-closed implementation stopped before the decision call. Replaying that saved response through the evidence broker selected 32 readings without another planner charge; shared readings meant every signal still received at least one selected reading. The over-request remains recorded rather than being hidden.

The selected evidence supported a complete low-reasoning Grok 4.6 review:

Staging therefore reduced peak context by 34.1% and cost by 51.2%, but increased total input work by 25.4%. It solves a context-window and model-tier problem; it is not yet more token-efficient overall.

The decision proposed four additions. Dependency-update automation recurred again with the same two readings and three signals. The other additions were developer documentation, current-term teaching status and timelines, and user authentication. The latter two overlap scope already named in the current Course list and detail views and Branding, navigation, and layout descriptions; the documentation proposal rests on one selected commit. These are provisional warnings, not adjudicated false positives, but they show that valid citations and complete signal accounting do not establish novelty against the existing map. No proposal was applied.

The next gate should explicitly review every proposal against its nearest existing nodes and allow the decision model to request a second evidence round when novelty or boundaries remain unclear. Only then should the staged condition be repeated for proposal stability.

What this establishes—and what it does not

The experiments establish that autonomous discovery can produce a recognizably coarse and substantially recurring umbrella hierarchy without being told the answer or a target count, that a separate assignment pass makes cross-cutting membership more reproducible, and that hierarchy formation accounts for more of the remaining variance than assignment alone. The disagreement pipeline establishes that a critic can account for every unstable input, preserve ambiguity, identify a recurring possible map gap without an owner-authored answer, and measure candidate anchoring separately from within-prompt variance. The hierarchy pilot establishes that those signals can drive sparse, validated structural proposals without automatically rewriting the map.

The experiments do not establish that any generated membership or proposed hierarchy change is correct, that child boundaries are dependable, that two levels are enough, or that the result generalizes beyond this repository. They do establish that proposal recurrence and protocol completion are separate gates: one stable proposal cannot make an incomplete critic reliable. Hierarchy changes still need a complete repeated condition measured against the pre-critic stability baseline, not a maintainer-authored target taxonomy.
